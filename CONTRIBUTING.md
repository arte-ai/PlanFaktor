# Planfaktor — как вносить изменения

Правила для меняющих этот репозиторий: что идёт через конвейер, что можно
править напрямую и что проверяют ревью и линт. Термины ролей, статусов
и гейтов — в конституции `AGENTS.md`, здесь без пересказа.

## Что это за репо

Plan-driven конвейер ролей, целиком в ZCode и без рантайма: истину
маршрутизации составляют статусы в файлах планов, не память чата.
Репозиторий — корпус контрактов (конституция, роли, команды, шаблоны)
и планов, которые эти контракты меняют. Порядок чтения: `README.md` →
`AGENTS.md` → `docs/lifecycle.md`.

## История репозитория

История git пересобрана 2026-11-13 из санитизированного архива: коммиты
до 34481ff — воспроизведение работы, даты коммитов — время пересборки,
а не время исходных событий.

## Как вносятся изменения

Два пути.

**Содержательные изменения** — код (`scripts/`, `.zcode/`), контракты
ролей (`docs/roles/*`), конституция (`AGENTS.md`), шаблоны — только
планом через конвейер: план из `docs/plans/_template.md`, диспатчи
Manager'ом (`/planfaktor-run`), Owner-гейт merge («мержим»),
ревью двумя ланами (risk → contracts); коммит делает только Manager
после Owner-«да», формат `type(PlanID): summary` (§8).

**Малые доки-правки** (опечатки, уточнения формулировок) — можно напрямую,
без плана, но:

- append-only логи планов (`## Evidence`, `## Q&A log` и другие) не
  переписываются: история — факты своего времени (§5);
- изменения контрактов (`AGENTS.md`, `docs/roles/*`, `.zcode/commands/*`,
  шаблоны) — не «малая правка»: §3 п.7 требует миграционной записи
  digest в `## Evidence` плана, значит — через конвейер.

## Дисциплина изменений

- Опирайся на актуальные файлы, не на память чата: статус и содержание —
  из перечитанного файла, не из обсуждения.
- Называй точные пути и статусы
  (`docs/plans/261111_2243_corpus_lint_ci.md`), а не «где-то в планах».
- Derived-поверхности руками не ведутся: очередь планов — производная от
  статусов в файлах (`/planfaktor-status` собирает её сам), отдельных
  индексов планов не заводят; `docs/followups/index.md` пересобирается при
  изменении `docs/followups/backlog.md`, а не правится при чтении; новая
  секция шаблона требует записи в `SECTION_CUTOFF` (`scripts/check_corpus.sh`),
  иначе проверка секций падает.
- Ничего не удаляй молча: отклонение от шаблона или процесса — fail
  loud, чинить чужую работу тихо нельзя (§5).
- Тесты и факты в плане должны быть воспроизводимыми командами: команда
  из `## Tests / Commands` обязана давать заявленный результат.

## Что должен уметь идентифицировать ревью

- покрытие DoD пункт-в-пункт: каждый пункт `## Acceptance criteria / DoD`
  закрыт evidence;
- выход за Scope и недоделанный Scope: лишнее так же плохо, как
  недоделанное;
- невоспроизводимые факты: «команда проходит» обязано подтверждаться её
  фактическим результатом;
- нарушение ownership-зон: секции плана несут метки `<!-- owner: ... -->`,
  чужие зоны не заполнялись;
- битые ссылки и форматы: относительные пути существуют, шапки планов и
  review-артефактов соответствуют парсеру.

Более широкую потребность, вскрытую работой, фиксируй bounded follow-up
в `## Follow-ups (deferred)` плана, а не расширяй изменение молча.

## Проверки

Линт корпуса:

```zsh
./scripts/check_corpus.sh             # инварианты C1–C12, итог `corpus: clean`
./scripts/check_corpus.sh --selftest  # линт проверяет сам себя: 15/15 caught
```

CI (`.github/workflows/corpus.yml`) гоняет обе команды на каждый push и PR.
Строка `**Status:**` в шапке плана — parser-контракт: Manager и линт грепают
её в фиксированной форме (одно из девяти значений §2), формат менять нельзя.

## Окружение

Работа идёт в ZCode: основная сессия Manager и субагенты-роли.
Рантайм-зависимостей нет, python не используется — линт это POSIX sh
и стандартные grep/sed. Достаточно работающего `git` и сессии с заранее
выданными правами записи (ops-заметка в конце `README.md`).
