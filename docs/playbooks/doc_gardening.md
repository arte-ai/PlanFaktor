# Doc gardening — регламентная гигиена канона

Периодическая (запуск — только по решению Owner) расчистка канона:
правила, дописанные планами, со временем обрастают прозой; gardening
переписывает правила в рецепты и убирает дубли, не меняя самих правил.
Норма чтения темы — effective spec: тема контура читается из самого
позднего плана + канона (`docs/plans/README.md`, раздел «Чтение темы»);
gardening работает против актуального канона, история не
пересказывается.

## Правила сессии gardening

- Одна тема — один раздел канона: сессия не прыгает между темами.
- Ограничение объёма: не более 3 файлов правок за сессию; нужно
  больше — это уже план (scope, DoD, ревью), а не расчистка.
- Каждое правило переписывается в рецепт: trigger (когда срабатывает)
  + скелет (шаги/форма) + проверка (как убедиться, что выполнено).
- Выход — один entrypoint на тему, покрывающий 80% кейсов: точка, из
  которой читатель входит в тему; минус дубли между разделами (дубль
  либо сводится к pointer'у, либо поглощается entrypoint'ом).
- Всплывшие работы (не гигиена, а изменение поведения) — 1–3 строки
  в `docs/followups/backlog.md`, не правка на месте.
- Сначала рецепт, потом ужесточение линта: новый чек вводится только
  после того, как правило стабильно записано рецептом — линт по
  неустоявшейся форме ловит формулировку, а не дефект.
- Перед сессией обязателен проход по
  `docs/playbooks/contract_edit_invariant_map.md`: классификация
  затрагиваемых блоков; hard invariant не трогается.

## Порядок

1. Решение Owner о запуске (gardening не самозапускается).
2. Выбор темы и раздела; инвентарь дублирующих мест (grep по якорям
   темы).
3. Invariant map по затронутым файлам.
4. Переписывание в рецепты; дубли → pointer; всплывшее → backlog.
5. Полный прогон `scripts/check_corpus.sh` — зелёный обязателен:
   линт держит грамматику, gardening держит прозу.
6. Изменения стейджатся; коммит — через обычный контур (план или
   прямое указание Owner). Gardening без плана правит только доки,
   не контракты; контракт — значит план.
