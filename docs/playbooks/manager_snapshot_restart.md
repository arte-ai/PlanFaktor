# Snapshot-рестарт Manager-сессии

Упреждающий контекст-чекпоинт Manager-сессии: сессии недолговечны
(простаивающие рвутся, возобновление = свежая сессия с полным handoff),
routing truth переживает смерть сессии (статусы в файлах, AGENTS.md §2),
а рабочий контекст — нет. Плейбук задаёт протокол упреждающего
чекпоинта и межсессионного рестарта. Дополняет §7 (recovery): §7 —
владелец аварийного восстановления (потеря хендла, терминальный
ступор); snapshot — упреждающая дисциплина, не замена и не дубль.

## 0. Быстрый рестарт

Свежая Manager-сессия начинает с этого блока (остальное — по мере
надобности):

- Где мы: Plan ID, статус, фаза роли, что ждёт (CENSOR / ревью /
  Owner-гейт).
- Кому передаём: конверт следующего диспатча
  (ROLE/PLAN_PATH/PRE_STATUS_LINE/ROLE_DOC/TASK).
- Next 1–3: конкретные микро-шаги очереди.
- Команды copy-paste: `grep -H '^\*\*Status:\*\*'
  docs/plans/[0-9]*.md`, `git status --short`, `git log --oneline -5`,
  `grep -n '(Role CENSOR)' docs/plans/<файл>`.
- Working set: изменённые/стейджнутые пути; unstaged append-only дельты
  плана и review-артефакта (штатны — §1(f), intake-записи).
- Branch/HEAD: текущая ветка и HEAD-коммит.
- Что уже прогоняли: команды проверок с датами и результатами — из
  `## Evidence` плана, не из памяти.
- Грабли-инварианты: топ ловушек текущего плана по схеме раздела 4.

## 1. Носитель и границы

- Носитель: `.tmp/snapshots/YYYYMMDD_HHMM_manager_<topic>.md` — имя
  латиницей; не коммитится: `.tmp/` уже исключён из git как рабочие
  материалы, не входящие в канон (`.gitignore`); репо публичный —
  сессионный контекст в историю не входит. Потеря `.tmp` при чистке
  допустима: durable факты обязаны быть промоучены в корпус (ниже).
- Граница: snapshot — history/handover, не source of truth и не cited
  pointer. Истина — файлы планов и канон; snapshot не конкурирует с
  ними, а ускоряет вход новой сессии.
- Ссылка на snapshot из канона (планов, конституции, роль-доков)
  запрещена: durable факт промоутируется в план (Evidence/Q&A)/канон/
  followups — туда, где ему положено жить, — и канон ссылается уже
  на него, не на snapshot.
- Цепочка Previous snapshot: каждый snapshot открывается строкой
  `Previous snapshot: .tmp/snapshots/<предыдущий>` (или
  `Previous snapshot: none` у первого) — история чекпоинтов для
  последовательного входа.

## 2. Контейнеры

Тело snapshot — плоские секции-контейнеры, не нарратив:

- FACT — проверенные факты с носителем (файл:строка; команда и
  результат).
- DECISION — решения сессии с указанием, где закреплены (секция
  плана / Q&A-пара).
- CONSTRAINT — действующие ограничения (Scope/Out of scope плана,
  гейты, запреты конституции).
- NEXT — очередь микро-шагов с исполнителем (роль / Manager / Owner).
- OPEN — открытые вопросы и допущения без закрытия.

Незнание не маскируется знанием: факт, не подтверждённый файлом,
помечается `UNCONFIRMED` — не додумывать; первая задача следующей
сессии — подтвердить его против репозитория или вычеркнуть.

## 3. Маскирование выхлопов

Выхлопы команд в snapshot маскируются: секреты, токены, приватные
данные — `[MASKED: <что замаскировано>]`. Рядом с маскированным
выхлопом обязана стоять команда воспроизведения (copy-paste): читатель
восстанавливает выхлоп сам, маска не рвёт repro-цепочку. Маскирование —
дисциплина этого плейбука; сканеры безопасности (если вводятся
отдельным планом) его не заменяют и не дублируются им.

## 4. Грабли

Каждая ловушка — по схеме:

- Repro: как воспроизвести (команда/шаг).
- Root cause: почему случилось.
- Fix: что исправляет.
- Regression test: как проверяется, что не вернётся (прогон/чек,
  который это ловит).

## 5. Когда снимать snapshot

- Перед ожидаемой паузой сессии (Owner-гейт, owner-silence, конец
  рабочего шага).
- Перед рискованной операцией (merge-рутина, recovery, ручные
  исправления).
- По самочувствию сессии: контекст вырос, шагов сделано много —
  снимай; восстановление из snapshot дешевле повторного чтения корпуса.
