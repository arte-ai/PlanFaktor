# Safe-git: аварийные состояния рабочего дерева

Рецепты для ролей и Manager-сессий, попавших в нештатное git-состояние.
Planfaktor работает в рабочем дереве main без веток (конституция §8),
поэтому любой уход с main — уже аномалия: первый шаг всегда — понять,
где вы сейчас, и не усугублять. Ничего не переписывайте молча: история
коммитов — общий актив, force-операции — только по явному решению
(ниже). Контекст конвейера: Recovery §7; терминальный ступор —
`manual_terminal_recovery.md`.

## Где я: ветка и HEAD

```sh
git status -sb          # текущая ветка/HEAD + грязность дерева
git branch --show-current   # пустой вывод = detached HEAD
```

Detached HEAD — вы вне ветки: новые коммиты будут висеть без ссылки.
Дальше — рецепт «Detached HEAD» ниже.

## Что уже запушено

Сначала синхронизируйте знание об удалёнке, потом сравнивайте:

```sh
git fetch origin
git log --oneline origin/main..HEAD   # коммиты впереди origin/main
git status -sb                        # behind/ahead считается после fetch
```

Пустой вывод `origin/main..HEAD` — локальных коммитов сверх удалёнки
нет. Есть коммиты — они ещё нигде, кроме вашей машины: потеря дерева
теряет их (см. «Потерянный коммит»).

## Незавершённый rebase

Признак: `git status` показывает «You are currently rebasing» или
существует `.git/rebase-merge`. Порядок:

1. Разрешите конфликты в файлах, `git add <файлы>`.
2. `git rebase --continue` — следующий шаг.
3. `git rebase --abort` — откат rebase целиком, дерево возвращается
   к состоянию до старта: безопасный выход, если не понимаете шаг.
4. `git rebase --skip` — редко и осознанно: пропуск коммита, чьи
   изменения уже есть upstream.

Rebase переписывает коммиты: пока он не завершён, не начинайте другие
операции с историей.

## Detached HEAD

Вернуться на ветку, если ничего ценного не сделано:

```sh
git switch main
```

Спасти коммит(ы), сделанные в detached HEAD:

```sh
git switch -c rescue/<topic>        # ветка на текущем HEAD
# или, когда HEAD уже ушёл дальше:
git branch rescue/<topic> <sha>     # ветка на конкретный коммит
```

`<topic>` — короткое имя причины (план/инцидент). Дальше — решайте
по контексту: merge rescue-ветки в main делает Manager (§8), не роль.

## Amend и force — только осознанно

- `git commit --amend` переписывает последний коммит. Коммит уже
  в origin — amend готовит расхождение истории с удалёнкой: любой push
  потребует force.
- `git push --force` / `--force-with-lease` — переписывание удалённой
  истории: допускается только по явному решению (Owner-гейт для
  публичной истории; §8 — коммиты делает Manager). `--force-with-lease`
  безопаснее голого force: отказывается от push, если удалёнка ушла
  вперёд, — но решение о переписывании принимает человек, не флаг.
- Ретроспективная чистка запушенных коммитов (утёкшие значения) —
  вне конвейера гигиены: защита действует вперёд (SECURITY.md).

## Потерянный коммит

Коммит, ставший недостижимым (reset мимо него, отвязанная rescue-ветка,
переписанный rebase'ем), живёт в reflog до сборки мусора:

```sh
git reflog                 # журнал перемещений HEAD: <sha> <описание>
git branch rescue/<topic> <sha>   # вернуть коммит в достижимость
```

Ищите строку с описанием нужного действия (commit/reset/rebase), берите
её `<sha>` и цепляйте rescue-веткой. После спасения — верните контекст
Manager'у: самовольный merge в main не делается (§8).
