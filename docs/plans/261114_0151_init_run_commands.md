## Как я понял задачу
<!-- owner: architect; 3–7 строк; обязательна при Architect intake -->

инициализация Manager-сессии без аргумента (bootstrap: свежее чтение
AGENTS.md и run.md с диска, корпус и ответы на русском, usage-учёт

## Problem
<!-- owner: architect; пронумерованные пункты -->

1. **Ядро A: нет разовой инициализации Manager-сессии.** Ни `run.md`,
   ни `plan.md` не предписывают: перечитать `AGENTS.md` и `run.md`
   с диска при старте сессии (`plan.md:17-18` — шаг 4 после вставки
   шага 3 preflight merge'ом 1944 — требует свежего чтения
   только `_template.md`); вести корпус и ответы по-русски (grep
   `русск` по корпусу вне планов/ревью — единственный hit
   `docs/roles/_template.md:13`, про имя роли); вести usage-учёт
   с первого диспатча (§1(f); канон форматов есть в `run.md` §3,
   но точка входа новой сессии его не транслирует — run.md начинается
   сразу с селекции); завершать каждый ход явным исходом — гейт/стоп/
   доклад; умолчание очереди (остальные Draft не трогать). Всё это
   существует только в живых хендоффах — вне файлов, против §5 «чего
   нет в файлах — не существует».
2. **Ядро B: run не принимает план — «указание Owner» без канонической
   формы, поведение при аргументе не определено.** `PLAN_PATH`
   в `.zcode/commands/` существует только как поле конверта диспатча,
   которое генерирует сам Manager (`planfaktor-plan.md:29` — строка
   сдвинулась шагом 3 preflight merge'а 1944, `planfaktor-run.md:65`);
   frontmatter всех трёх команд — только
   `description`, входного аргумента нет ни у одной (grep
   `PLAN_PATH|$ARGUMENTS`). Старт конкретного Draft очереди сегодня —
   свободным текстом: fresh-диспатч 2121 (Evidence 23:27:16
   «Owner-указание: вести этот план первым из пяти черновиков»),
   создание этого плана (Evidence: «старт Draft-плана свободным текстом,
   ручной хендофф Manager-сессии, смешение выбора и продолжения
   в /planfaktor-run»). `run.md:17` — «`Draft` селекцией не выбирается:
   резюмируется по указанию Owner» — что считается указанием и куда его
   подавать, корпус не определяет. Получив аргумент, run ведёт себя
   неопределённо (молчаливое игнорирование или свободная
   интерпретация) — fail-loud-ветки нет, контраст с §5.
3. **Носители входной двери разъедутся при четвёртой команде.**
   `README.md:39-43` — «Три команды» (bullet-список, без примеров
   вызова); `CONTRIBUTING.md:28` упоминает из команд только
   `/planfaktor-run`; `docs/plans/README.md:27-30` — правило очереди
   без маршрута запуска Draft; `docs/getting_started.md` (новый носитель
   merge'ом fc3cc79 после intake 02:04 — сверен в этой итерации) —
   «три команды» в трёх местах: перечисление в таблице копирования
   (:32), «в чате работают три команды Manager'а» (:67), таблица
   «Команды Manager'а» (:103-109), плюс сценарий первого запуска
   (:73-91) ведёт планом/run-без-аргумента, без инициализации сессии.
   `docs/lifecycle.md` команды не описывает
   (grep `planfaktor-|команд` → 0) — синхрон для него не нужен.
   Пересечений с существующими командами нет: `planfaktor-plan.md`

## Solution / Decisions
<!-- owner: architect; решения уровня «что и почему», без детализации -->

1. **`/planfaktor-init` — разовая инициализация Manager-сессии, без
   аргумента** (новый файл `.zcode/commands/planfaktor-init.md`):
   перечитать `AGENTS.md` и `run.md` с диска (свежее чтение, не память
   чата); весь корпус и ответы сессии — на русском; usage-учёт
   с первого диспатча (§1(f); канон форматов — `run.md` §3 и комментарий
   шаблона, в init не дублируется — третий носитель создал бы дрейф);
   каждый ход завершается явной строкой — гейт (ждать Owner) / стоп
   (причина) / доклад по рутине; очередь управляется переходами
   статусов, остальные Draft не трогаются (решение 2121). Вызывается
   один раз на старте сессии; повторный вызов идемпотентен —
   перечитать контракты, доложить состояние очереди; команда ничего
   не знает о конкретных планах (никакой селекции и диспатчей).
   Прежняя альтернатива «init с PLAN_PATH» (итерация Architect'а
   01:58) снята Owner-коррекцией: смешение инициализации и выбора
   плана воспроизводило бы исходную friction-точку — выбор
   и продолжение в одной команде; указание плана — зона run.
2. **`/planfaktor-run [PLAN_PATH]` — ведение/старт планов; опциональный
   аргумент — каноническая форма Owner-указания.** Без аргумента —
   селекция шага 1 (пост-2121) без изменений. С аргументом (путь
   или Plan ID; при Plan ID — разрешение glob'ом
   `docs/plans/<ID>_*.md`, неоднозначность — fail loud): валидации —
   файл существует; `**Plan ID:**` ↔ префикс имени (форма C2,
   `scripts/check_corpus.sh:207-225` — строки сдвинул C14 merge'а
   1944); статус ∈ {`Draft`,
   `Ready for *`}, иные → fail loud «продолжай без аргумента»
   (селекция); «один активный план» §2 — другой план в
   `Ready for *`/`In progress`/`In review`/`Merged` → стоп-вопрос
   Owner. Draft-ветвление по факту дерева, не по памяти: (а)
   Architect-секции непусты сверх шаблонных комментариев и intake роли
   в `## Q&A log` нет — кураторский черновик §1(g): диспатч
   `planfaktor-architect` на перепринятие (не rubber-stamp) + CENSOR §4
   → `Ready for Planner`; (б) план пуст (только шапка) — диспатч
   Architect-фазы по брифу Owner (бриф = сопроводительное сообщение
   команды; пуст — спросить, прецедент `planfaktor-plan.md:7`) тем же
   CENSOR-циклом; (в) intake уже есть (откат FAIL оставил Draft
   с начатой фазой) — диспатч на продолжение фазы (§7). После
   валидного CENSOR — ретрансляция Owner'у «Как я понял задачу» +
   границ Scope (дословно, точка чтения человека §2) и доклад
   открытых вопросов; далее — run без аргумента. Активация
   `Ready for *`: Evidence-узел активации (кто инициировал, план,
   спец-указания; зона §1(e)) + продолжение по routing-таблице.
   Строка Draft-резюмы `run.md:17` получает указатель: указание
   Owner = `/planfaktor-run <PLAN_PATH>`.
3. **Синхрон носителей:** `README.md` — «Три команды» становится
   «Четыре команды» таблицей (команда | назначение) с примерами
   `/planfaktor-init` (разовый старт сессии) и
   `/planfaktor-run <PLAN_PATH>` (каноническое указание плана);
   `CONTRIBUTING.md` — команды в контексте «Как вносятся изменения»;
   `docs/plans/README.md` — строка навигации запуска: инициализация
   сессии — `/planfaktor-init`, активация Draft очереди —
   `/planfaktor-run <PLAN_PATH>`; `docs/getting_started.md` — все три
   перечисления «трёх команд» (таблица копирования :32, строка :67,
   таблица :103-109) расширяются до четырёх, сценарий первого запуска
   (шаг 2) получает `/planfaktor-init` после открытия ZCode в корне;
   скриншоты 02/03 таблиц и перечней команд не несут (шапка плана,
   status-доклад по подписям гайда); `01-install-tree.png` несёт
   перечень файлов `planfaktor-{plan,run,status}.md` (сверено
   визуально в цензорной итерации) — после четвёртой команды
   устаревает, пересъёмка — ручная операция вне конвейера, кандидат
   follow-up (Out of scope); текстовая часть гайда синхронизируется
   планом. `docs/lifecycle.md` не меняется:
   команд не описывает (Problem п.3).
4. **Миграции §3 п.7 без правки конституции.** Перечень контрактов
   в §3 п.7 открытый — glob `.zcode/commands/*` (AGENTS.md:148)
   покрывает новый файл, дополнять список не нужно. Записи по этому
   плану: `planfaktor-run.md: @1d02ddb1 → <новый>` (базовый digest —
   финал цепочки 2121 → merge 1943 (`@ccf9685b`) → merge 1944
   (`@1d02ddb1`), смена зафиксирована Evidence плана 1944
   (22:51:29), диск = записям — перепроверено `shasum` в этой
   итерации, живого дрейфа нет) и
   `planfaktor-init.md` — новый контракт, запись создания с digest'ом
   (без старого значения). `AGENTS.md` и `planfaktor-plan.md` этим
   планом не правятся — их смены digest (`@1f66a38f`, `@27f10905`)
   принадлежат плану 1944, новых миграций не порождают.
   `AGENTS.md` §1 и его навигационная копия
   `docs/roles/index.md:12` не меняются: §1 — не реестр команд
   (`/planfaktor-plan` и `/planfaktor-status` там тоже не упомянуты,
   прецедент); норма index — «правка вместе с §1».
5. **DoD-каркас (зона Planner, предложения):** init существует, без
   планового аргумента, идемпотентность прописана; bootstrap-инварианты
   п.1 grep-проверяемыми якорями; run: ветка с аргументом — валидации
   и Draft-ветвление п.2 якорями; run без аргумента — инварианты базы
   2121 (`резюмируется` → 1, `^| `Planning` |` → 1, `спроси Owner,
   какой вести` → 0 — все три якоря перепроверены по текущему run.md);
   README и `docs/getting_started.md` несут перечень/таблицы четырёх
   команд с примерами `/planfaktor-init` и
   `/planfaktor-run <PLAN_PATH>` (getting_started — во всех трёх
   местах перечисления, Solution п.3); миграционные записи п.4;
   самоприменение — первый план Owner-выбора после merge этого плана
   запускается `/planfaktor-run <PLAN_PATH>` без ручного
   многострочного хендоффа (исходная цель 261113_1644 устарела —
   смержен и закрыт до этой итерации; Draft-очередь на момент intake
   пуста, этот план — единственный): checker на исполнении
   (Evidence-узел активации в плане-преемнике), не линт; при живом
   другом активном плане сработает стоп-вопрос «один активный» —
   штатный инвариант §2, решение за Owner; регрессия —
   `corpus: clean` + selftest (C9 требует
   наличия файла команды при упоминании `/planfaktor-init` — файл
   появляется тем же планом; новый `planfaktor-init.md` сам становится
   C9-источником относительных путей; C10 не затронут: команды —
   не агенты).
