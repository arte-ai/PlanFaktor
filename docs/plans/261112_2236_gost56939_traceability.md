## Problem
<!-- owner: architect; пронумерованные пункты -->

1. Стандарт (раздел 5.3) требует набор требований безопасности с
   идентификаторами, приоритетами, сроками и сведениями о предъявивших/
   принявших (5.3.3.2), учёт артефактов со сведениями о принятии, текущем
   статусе, изменениях статуса и изменениях самих требований (5.3.3.3),
   регламент управления (5.3.3.1) — у Planfaktor нет носителя внешних
   требований: трасса начинается от плана, вход разомкнут.
2. Прослеживаемость устранения ошибок (п. 4.13) и управление
   недостатками с уникальными ID и статусами (5.5.3.3) — примитивы есть
   (followups: id/status/priority/disposition+ref; коммиты
   `type(PlanID)`), но связь с требованиями и привязка версии не
   формализованы.
3. Карта покрытия DoD↔Tests живёт внутри планов (метки Dn), корпусно не
   агрегируется; линт не проверяет R-привязки и покрытие R-DoD тестами.
4. Клиенту нужен предъявляемый документ: какими механизмами и
   артефактами Planfaktor закрывает пункты стандарта — маппинга нет.

## Solution / Decisions
<!-- owner: architect; решения уровня «что и почему», без детализации -->

1. **Реестр требований** `docs/requirements/registry.md`. Row-грамматика
   — ровно 8 полей / 7 разделителей ` — ` (правило: формулировка не
   содержит ` — `; enforce — подсчётом полей в C12):

   ```
   - <ID> — <формулировка> — предъявлено=<YYYY-MM-DD, кем> — принято=<none|<кем>, <YYYY-MM-DD>> — приоритет=<P1|P2|P3> — срок=<YYYY-MM-DD|none> — статус=<open|planned|verified> — plan=<PlanID|none>
   ```

   ID: `REQ-<n>` (клиентские) или `G56939-<пункт>`. Статусный enum —
   `open|planned|verified` (статуса `released` НЕТ до релизной конвенции
   — backlog row `release-node`; false-обещание клиенту не даём).
   Секция `## Журнал статусов` (append-only) — два типа записей:
   `- <TS> — <ID>: <статус1> → <статус2> — <PlanID|commit>` и
   `- <TS> — <ID>: требование изменено (<что>: <было> → <стало>) — <почему>`
   — закрывает 5.3.3.2 и все четыре ветки 5.3.3.3 (принятие, текущий
   статус, изменения статуса, изменения требований).
2. **Регламент** `docs/requirements/README.md` (5.3.3.1): предъявление
   (Owner-бриф → Architect intake → row: `принято=` заполняется
   Architect'ом), предоставление (R-метки в плане), отслеживание
   (статусы по гейтам: `planned` на Ready for Coder, `verified` на
   Merged — переводит Manager в Evidence-узле merge и журнале),
   критерии пересмотра (5.3.2.4): событийные — Superseded плана,
   изменение конституции, решение Owner; периодический пересмотр не
   проводится (обоснование: один Owner, событийные триггеры покрывают
   цикл изменений).
3. **R-метки в планах**: в `## Scope` и в DoD-пунктах, реализующих
   внешние требования, метка `[R: <ID>]` (шаблон: комментарий секций
   Scope/DoD дополняется формой; Tests-комментарий — правилом
   «покрывать Dn всех R-DoD»). Трасса входа замкнута.
4. **Матрица трассируемости** `docs/requirements/matrix.md` — derived
   view: `ID → планы → DoD(Dn) → Tests(Tn) → review → коммиты → статус`;
   v1 — правила пересборки + grep-рецепт (прототип проверен: 0.12 с);
   автогенерация — кандидат v2. Считать только тела секций (полнофайловый
   счёт ловит прозу).
5. **Комплаенс-маппинг** `docs/compliance/gost-r-56939-2024.md` —
   предъявляемый клиенту документ: `пункт стандарта → механизм
   Planfaktor → артефакт-носитель → статус (реализовано/частично/вне
   скоупа)` по 4.11–4.13, 5.3.x, 5.4, 5.5.x, 5.9, 5.18, 5.20. Честные
   границы: 5.7/5.10–5.17 — чужие инструменты, «вне скоупа конвейера»;
   5.5.3.3 «версия ПО» — частично (привязка через plan=/commit, релизной
   версии нет); 5.5 «запросы на изменение» как отдельный класс —
   частично (backlog не разделяет недостатки и запросы).
6. **Недостатки (5.5.3.3)**: `docs/followups/_template.md` дополняется
   правилом — недостатки ПО фиксируются rows с обязательной привязкой
   версии (`plan=`/`source_ref` на коммит). Перекрёстные ссылки (5.5.2.5):
   коммиты `type(PlanID)` ↔ планы ↔ backlog id — фиксируются в маппинге.
7. **Линт C12** (детектор — секционно-якорный: тела `## Scope` и
