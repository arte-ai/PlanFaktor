## Как я понял задачу
<!-- owner: architect; 3–7 строк; обязательна при Architect intake -->

Handoff между ролями файловый: его честность — то, что роль-получатель
может сделать буквально, без угадывания. Сегодня план бывает формально
заполнен, но оставляет Coder'у/Reviewer'у догадки, «обещанные» проверки
без материального носителя, у Coder нет протокола исходов по каждому
DoD-пункту до правок, а допущения и отсутствие контента не имеют
легальной формы записи. По модели предков (приватные первоисточники)
вводим: завершающий самопроход Planner'а глазами потребителя, закрытый
набор исходов Coder'а по DoD (AC-to-test), Assumption-протокол,
универсальную форму отсутствия `N/A (why=...)`, контент-факты цензорных
«нет находок», метку `Review verdict seen`, дисциплину untrusted
specialist input и intake-чеклист Architect'а из 11 классов; Corpus lint
не расширяем. План процессный: меняются только контракты и шаблоны,
кода нет. Усиления Owner: A/B-фиксация выбора, narrow+broad proof при
переименованиях, позитивная зона решений Coder'а. Соседние черновики
2121/1642 смержены — их механики (Q#n-грамматика Q&A, reroute-
классификация, No findings reason:, B-блоки/Rerun, C13, §1(g)
кураторство) теперь факты контрактов: этот план дополняет, не дублирует;
перепринятие 2026-11-14 сверено с текущим деревом.

## Problem
<!-- owner: architect; пронумерованные пункты -->

1. **Handoff Planner → Coder не имеет обязательной самопроверки глазами
   потребителя.** Условие перехода `Planning → Ready for Coder` — «DoD/Tests
   заполнены; Planner CENSOR OK» (AGENTS.md §2), фаза Planner'а
   (docs/roles/planner.md) заканчивается заполнением секций; CENSOR —
   второй угол уже после простановки статуса. Нет обязательного прохода,
   который до handoff ловит два класса дефектов: (а) то, что Coder и
   Reviewer, буквально следуя плану, будут вынуждены угадывать, и где тот
   же блокер переживёт handoff; (б) обещанные доказательства без
   материального носителя — способ проверки назван, а команды/файла/строки
   нет (implicit proof). Эти дефекты всплывают дороже — в `In progress` /
   `In review` (loop-класс §6). База: `rg -ni 'глазами|completion|угадыва|implicit'`
   по всем контрактам → 0.
2. **У Coder нет протокола связывания DoD → доказательство до правок.**
   coder.md требует реализации по Scope/DoD и прогонов Tests, но не требует
   явного исхода по каждому DoD-пункту до начала правок. Пробел
   обнаруживается цензором или ревью, а случай «доказать нельзя без
   расширения скоупа» вообще не имеет легального пути возврата до правок —
   сегодня он решается молчаливой импровизацией. База (перепринято
   2026-11-14 против текущего дерева): `rg -ni 'explicit assertion|
   existing proof'` → 0 — исходов AC-to-test нет ни в одном контракте;
   лексема `reroute` после мерджа 261113_1642 занята reopened-классификацией
   ревью-возврата (AGENTS.md §2, docs/roles/architect.md) — протокола
   исходов DoD у Coder'а она не даёт.
3. **Допущения Coder'а не имеют носителя, правило возврата чужой зоны
   не кодифицировано универсально.** Формы `Assumption:` нет нигде
   (rg → 0): допущение живёт в голове роли и всплывает из кода на ревью.
   «Не чинить молча» разбросано точечно: §5 fail loud — про Manager'а,
   coder.md/planner.md — каждый про себя; ревьюер-доки формы возврата
   чужой зоны не несут (перепринято 2026-11-14: `objection` → 0;
   «молчаливый повтор»/«пустого молчания нет» в reviewer-risk.md:23,30 —
   механика смерженного 1642 про молчание собственных находок ревьюера,
   не про возврат чужой зоны). Молчаливая реализация допущения,
   меняющего Scope/DoD/контракты, сегодня не блокируется до ревью.
4. **Явная форма отсутствия точечна, а не универсальна.** Есть:
   `NO QUESTIONS / NO SUGGESTIONS / NO OBJECTIONS` (§3), закрытие Q&A
   `A(...): status=closed`, `NO FOLLOW-UPS — why:` (шаблон плана), `plan=none`
   (backlog). Нет общего правила для обязательных полей плана/ревью:
   контент-пустота сегодня легальна — `Fixes: <что исправлено / ничего>`
   допускает голое «ничего» (AGENTS.md:168), а класс `TBD/пусто/UNCONFIRMED`
   нигде не запрещён (в актуальных контрактах вхождений нет — rg → 0,
   запрет как норма отсутствует). Перепринято 2026-11-14: findings-пустота
   review-артефакта закрыта смерженным 1642 формой `No findings reason:`
   (_template_review.md:39/84/127) — пример снят, дельта п.4 сужена до
   полей без специализированной формы. База: `rg -n 'N/A \(why='` → 0.
5. **Цензорный receipt: «нет находок» безнаказанно пуст, проходы после
   ревью не связаны с вердиктом ревью.** `Fixes:` и `Final censor verdict`
   уже обязательны (§4 — присутствует, в Problem не входит); deadlock-режим
   §4 (Loop signal в receipt — смерженный 1642) покрывает только
   подтверждённый файлами повторный loop и этих дельт не закрывает; дельты две:
   (а) форма отсутствия для `Fixes:` не требует контент-фактов —
   `NO FINDINGS` без перечня «что искал/проверил» сегодня валиден, хотя
   Counterfactuals/Addendum «обязательно при "дефектов не нашёл"» дают
   для этого материал; (б) для цензорных проходов раундов fixes (rN)
   нет метки `Review verdict seen` — цензор rN не обязан подтверждать,
   что видел вердикт review-артефакта последнего Round, из которого
   вытекают fixes (rg 'Review verdict seen|NO FINDINGS' → 0).
6. **Утверждения субагентов переносятся в артефакты без обязательной
   верификации.** §5 «Notice ≠ mutation truth» покрывает только Manager'а
   и только результаты мутаций («Manager верит grep'у, не отчёту»).
   Принцип untrusted specialist input — утверждения любой роли (цитаты,
   базы, «уже проверено») не принимаются на веру, а сверяются с
   репозиторием/первичными артефактами тем, кто на них опирается, —
   не кодифицирован ни для ролей, перепринимающих черновики, ни для
   переноса ответов Q&A в секции (rg 'untrusted|на веру' → 0; поля доверия
   Rerun mode смерженного 1642 — декларация собственного рерана ревьюером,
   не перепринятие чужих утверждений).
7. **У Architect'а нет intake-чеклиста постановки.** architect.md требует
   «Как я понял задачу» 3–7 строк, но без перечня классов вопросов —
   полнота понимания зависит от наития роли; бриф Owner может не закрыть
   класс (поведение; данные; SLA/производительность; безопасность;
   интеграции; проверяемость; релизные ограничения; UX-тексты;
   пост-мутационные обновления интерфейсов; инварианты данных
   с валидацией; синхронные доки), и пробел уйдёт в Planner'а как
   plan-gap вместо вопроса на входе.

## Solution / Decisions
<!-- owner: architect; решения уровня «что и почему», без детализации -->

1. **Planner finalize completion-pass — конституционное условие handoff.**
   §2: условие перехода `Planning → Ready for Coder` расширяется — «DoD/Tests
   заполнены; finalize completion-pass записан; Planner CENSOR OK».
   Механика — в docs/roles/planner.md (анти-дрейф: чек-листы в роль-доке,
   конституция — только статусная модель): перед простановкой статуса
   обязательный второй проход «глазами Coder и Reviewer» с дословным
   вопросом-самопроверкой «если Coder и Reviewer буквально последуют этому
   плану, что им ещё придётся угадывать и где тот же блокер переживёт
   handoff?»; любой ответ кроме «ничего» — дефект Planner'а, чинится
   до handoff. Плюс anti-false-green вопрос: «не осталось ли обещанное
   доказательство/проверка implicit — способ назван, а материального
   носителя (команда/файл/строка) нет?». Исход прохода — append-only
   запись в Evidence до простановки статуса; Planner CENSOR сверяет
   её наличие и вердикт. Почему до handoff, а не в CENSOR: находки
   меняют содержание DoD/Tests — это авторство, а не сверка.
2. **AC-to-test: закрытый набор исходов по каждому DoD-пункту.** Дисциплина
   §5 + детализация в coder.md: до начала правок по каждому пункту DoD
   фиксируется ровно один исход из закрытого набора: `explicit assertion`
   (новая проверка, ref) | `existing proof` (уже есть в корпусе, ref) |
   `N/A (why=...)` | `reroute` (доказать нельзя без расширения скоупа —
   стоп-линия: возврат роли-владельцу дефекта — DoD/Tests → Planner,
   решения → Architect — objection'ом/вопросом, не молчаливой заменой).
   Фиксация — append-only в Evidence до заполнения Changes. Закрытый
   набор исключает полузакрытия («DoD покрыт» словами) и делает reroute
   легальным до правок, а не находкой ревью.
   Разграничитель омонима: `reroute` здесь — исход DoD-пункта у Coder'а
   (стоп-линия до правок), не класс повторного блокера same-contract
   reroute из смерженного плана 261113_1642 (теперь §2 конституции,
   architect.md, грамматика review-артефакта) — одна лексема, две
   механики; омонимия уже живая (grep 'reroute' по контрактам несёт
   reopened-грамматику: AGENTS.md §2, lifecycle, plans/README, run.md,
   роль-доки), разграничитель обязателен для читателей и будущего
   qa-lint (различение — контекстом: AC-to-test у Coder'а до правок
   vs классификация ревью-возврата после ревью).
3. **Assumption-протокол + универсальное «не чинить молча».** Любое
   допущение Coder'а — строка `Assumption: ...` в `## Q&A log`
   (append-only; грамматика — в комментарий секции шаблона плана).
   Допущение, влияющее на Scope/DoD/контракты, — стоп и возврат
   на Planner (objection/вопрос), не молчаливая реализация. Правило
   «не чинить молча чужую зону — вернуть с objections» кодифицируется
   для всех ролей одной формулировкой в §5 (расширение fail loud);
   роль-доки не дублируют (анти-дрейф), ревьюер-доки наследуют
   из конституции.
4. **`N/A (why=...)` — единственная легальная форма отсутствия.** Принцип
   в §5: любое обязательное поле плана/ревью несёт контент или явную
   форму отсутствия с why; `TBD`/пусто/`UNCONFIRMED` невалидны как класс.
   Специализированные существующие формы (`NO QUESTIONS...`, `NO
   FOLLOW-UPS — why:`, `plan=none`, `No findings reason:`) не меняются —
   общая форма закрывает поля без специализированной. Точки применения:
   комментарий секции в `docs/plans/_template.md`, обязательные поля
   review-артефакта без специализированной формы отсутствия
   (`docs/reviews/_template_review.md`), грамматика
   в `docs/plans/README.md`.
   Приоритет специализированной формы: ревью-форма `No findings reason:`
   введена смерженным планом 261113_1642 (шаблон:39/84/127, роль-доки
   ревьюеров) и имеет приоритет в findings review-артефакта —
   универсальная `N/A (why=...)` её не дублирует и не заменяет; правило
   «специализированная форма старше общей» действует и для будущих
   специализированных форм.
5. **CENSOR-receipt: контент-факты для отсутствия и связь с вердиктом
   ревью.** §4: `Fixes:` обязателен всегда; при отсутствии находок —
   форма `Fixes: none (NO FINDINGS; <контент-факты — что искал/проверил>)`;
   `NO FINDINGS` без контент-фактов невалиден (связка с Counterfactuals/
   Addendum «обязательно при "дефектов не нашёл"»). Для цензорных проходов
   fixes-итераций Coder'а (rN; в грамматике смерженного 1642 — раунды
   `**Round:**` ≥ 2 review-артефакта) — обязательная метка
   `Review verdict seen: <Round, вердикт>`: подтверждение, что цензор
   прочитал вердикт review-артефакта последнего Round; обычные
   (доревьюерные) CENSOR-проходы метку не несут; сосуществует
   с deadlock-режимом §4 (Loop signal — отдельный случай подтверждённого
   файлами лупа, друг друга не заменяют).
   `.zcode/commands/planfaktor-run.md`: при валидации rN-receipt Manager
   грепает якорь `Review verdict seen` (одна строка в гейте шага 3,
   рядом с существующим блоком grep-проверок receipt).
6. **Untrusted specialist input — дисциплина §5.** Утверждения любой роли
   или субагента (цитаты, базы, «уже проверено», digest-значения)
   верифицируются против репозитория/первичных артефактов тем, кто на них
   опирается; перенос чужого утверждения в свою секцию без сверки —
   дефект. Отличие от «Notice ≠ mutation truth»: то правило — Manager
   и мутации; это — все роли и любые утверждения, включая переприятие
   черновиков и перенос ответов Q&A.
7. **Intake-чеклист Architect-фазы.** architect.md: 11 классов вопросов
   постановки (поведение; данные; SLA/производительность; безопасность;
   интеграции; как проверяем; релизные ограничения; UX-тексты;
   пост-мутационные обновления интерфейсов; инварианты данных
   с валидацией; синхронные доки) — как опора для «Как я понял задачу»:
   каждый класс закрыт брифом/корпусом, либо Q(...) к Owner, либо явное
   `N/A (why=...)`. Компактно, роль-док остаётся ≤ 250 строк (анти-дрейф).
8. **Corpus lint не трогаем** — осознанно (расширение линта — отдельный
   backlog-хвост lint-v2: `lint-v2-digest-verify`, `qa-lint`).
   Перепринято 2026-11-14: после мерджа 1642 линт — C1–C13 (C13 —
   грамматика live-блокеров/rerun review-артефактов). Совместимость новых
   форм с текущим исходником `scripts/check_corpus.sh` перепроверена:
   C4 требует у receipt-маркера префикс метки времени и наличие
   `Censor dispatch id:`/`Final censor verdict:` — дополнение блока
   строками `Review verdict seen:`/`Fixes: none (NO FINDINGS; ...)`
   не ломает; C5 регламентирует только Intake-строки (`Assumption:`
   свободна); C6 — новые тексты не создают `@hex`-хвостов; C7 —
   вердикт-строки ревью не переформатируются; C13 валидирует записанную
   форму B-блоков/Coverage/судеб — правки review-шаблона этим планом
   касаются комментариев и полей вне зоны 1642, B-блоки/Rerun/судьбы
   не затрагиваются. Регрессионный инвариант: полный прогон линта
   остаётся clean (факт-базы — зона Planner).
9. **Синхронизация справочников и миграции.** `docs/lifecycle.md` —
   синхронные описания фаз Planning (completion-pass), In progress
   (AC-to-test/Assumption) и выжимки CENSOR. Миграции §3 п.7 по каждому
   изменённому контракту — в Evidence этого плана (зона Coder,
   `<файл>: старый@8hex → @новый8hex`, с меткой времени).
10. **A/B-фиксация выбора: развилка живёт в Q&A, решение переписывает
    пункт.** Пока выбор между вариантами не сделан — это открытый Q&A
    (`status=open`): Solution/DoD не вправе нести «либо/или» — иначе
    Coder получает развилку вместо решения (plan-gap, §6). Выбор сделан —
    пункт секции-владельца переписывается в финальную формулировку без
    дизъюнкции (правка своей содержательной секции; append-only логи
    Q&A/Evidence при этом не переписываются — история выбора остаётся
    в Q&A-паре), отклонённая альтернатива сохраняется одной строкой
    `rejected alternative: <вариант> — why: <основание>`, добавляются 1–2
    acceptance-пункта, делающие решение проверяемым (оформление в DoD —
    зона Planner). Носители: §5 (дисциплина) + `docs/plans/README.md`
    (грамматика). Почему: «альтернативы с обоснованием отказа» уже
    обязательны для Architect'а (docs/roles/architect.md:10), но паттерна
    закрытия развилки нет — живой прецедент незанесённого в конституцию
    решения: выбор (а) по конвенции closeout-хвоста принят Owner'ом
    2026-11-12 и живёт только в Evidence (261112_0111:276, дословно),
    пункт конституции §8 не переписан, отклонённая альтернатива строкой
    не зафиксирована (backlog id=closeout-tail-convention, status=open —
    открыта только нормализация §8). A/B-механика закрывает именно этот
    класс: решение → финальная формулировка пункта + rejected
    alternative. База: rg 'rejected alternative|отклонённая альтернат'
    по контрактам → 0 (перепринято 2026-11-14; прецеденты подтверждены
    чтением: Evidence 261112_0111:276, backlog:10 status=open).
11. **Narrow + broad proof при переименованиях и миграциях терминологии.**
    Если план переименовывает токен/термин (формулировку команды, метку
    формата), Tests обязаны комбинировать два proof'а: narrow — exact-паттерн
    нового wording (появился там, где ожидалось, с базой «сейчас 0», если
    различающий) и broad — prose-drift старого токена: старый термин
    ищется по всем активным носителям (исторические планы и append-only
    артефакты исключены — там старое имя остаётся вечно), и вхождения
    классифицируются: остался ли старый вызов/значение, а не только
    легитимное упоминание. Один narrow даёт false-green (новое имя
    появилось, старое осталось в prose), один broad — false-red
    (легитимные исторические упоминания). Носители: комментарий
    `## Tests / Commands` в `docs/plans/_template.md` + `docs/plans/README.md`.
