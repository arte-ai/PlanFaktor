# Follow-ups backlog — шаблон

Шаблон носителя техдолга: `docs/followups/backlog.md` и будущие
тематические backlog'и этого каталога. Планы (`docs/plans/`) — контракт
на реализацию; накопленный техдолг между планами живёт здесь.

## Row-грамматика

Одна строка = один follow-up:

`- P? [ ] <summary> — to=<роль|Owner> — status=open|promoted|handled|cancelled — plan=<PlanID|none> — id=<kebab-id> — source_ref=<относительный путь[#секция]> — why=<кратко>`

- `P?` — приоритет: P1|P2|P3; `[ ]`/`[x]` — визуальный дубль статуса
  (open — `[ ]`, остальные — `[x]`).
- `to=` — исполнитель: Owner или роль из §1 конституции.
- `id=` — стабильный kebab-id, не переиспользуется.
- `source_ref=` — относительный путь существующего файла корпуса,
  опционально якорь `#секция`; абсолютные пути запрещены.
- `why=` — краткое обоснование: почему хвост не закрыт сейчас.

## Правила

- Техдолг НЕ заводится как tasks-only план — он живёт здесь строкой
  `status=open, plan=none`; когда хвост готов к реализации, заводится
  отдельный план в `docs/plans/`, а строка обновляется:
  `plan=<PlanID>`, `status=promoted`.
- `status=handled` требует disposition: ссылку на коммит/файл, где хвост
  фактически закрыт (в `why=` или следом за строкой). Проза «сделали»
  закрытием не считается.
- `status=cancelled` — только с `why=` (причина снятия).
- Недостатки ПО (ГОСТ Р 56939-2024, 5.5.3.3) фиксируются rows
  с обязательной привязкой версии: `plan=<PlanID>` плана, закрывшего
  недостаток, и/или `source_ref` на коммит/файл с правкой; row без
  привязки версии недостатком ПО не считается (клиентский запрос —
  с `id=` и `why=` как обычно, до разделения классов в v2).
- `summary`, `id`, `source_ref` стабильны; меняются только поля
  жизненного цикла (`[ ]`→`[x]`, `status`, `plan`, `why` при смене
  причины).
- `docs/followups/index.md` — derived view: пересобирается после каждого
  изменения backlog; при чтении руками не правится.
