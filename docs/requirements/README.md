# Управление требованиями — регламент (ГОСТ Р 56939-2024, 5.3.3.1)

Каталог `docs/requirements/` — вход трассы «требование → план →
изменение → верификация → релиз» конвейера Planfaktor:

- `registry.md` — реестр внешних требований (row-грамматика 8 полей +
  журнал статусов);
- `matrix.md` — derived-матрица трассируемости (пересобирается, руками
  не ведётся);
- этот файл — регламент жизненного цикла требований (5.3.3.1:
  положения о предъявлении, предоставлении, отслеживании, критериях
  пересмотра).

Машинные инварианты форм — линт C12 (`scripts/check_corpus.sh`):
существование R-меток в реестре, валидность rows, покрытие R-DoD
тестами. Комплаенс-маппинг стандарта целиком —
`docs/compliance/gost-r-56939-2024.md`.

## Предъявление

Внешнее требование (клиентское или нормативное) предъявляет Owner:
брифом в чате (для клиентских) или со ссылкой на пункт нормативного
документа (для стандартов). Architect при intake плана переносит
требование в реестр: новая row по формату (`registry.md`, раздел
«Формат row») со всеми 8 полями, `статус=open`, `plan=none`; поле
`принято=` заполняется тем же intake — кто принял к реализации и дата
(сведения о принятии, 5.3.3.3). Дата и предъявивший — в `предъявлено=`
(5.3.3.2). Первоначальный статус — часть row, отдельная запись журнала
не требуется.

## Предоставление

Требование предоставляется исполнителям R-метками в планах: пункт
`## Scope` или пункт DoD, реализующий внешнее требование, несёт
`[R: <ID>]` (форма — в комментариях секций `docs/plans/_template.md`).
Трасса замыкается: реестр → план (R-метка) → DoD/Tests → review →
коммит `type(PlanID)`. Свежесть меток контролируется на двух углах:
линт C12(а) (существование ID) и contracts-лан review (правило в
`docs/reviews/_template_review.md`). Клиенту требование предоставляется
через комплаенс-маппинг `docs/compliance/gost-r-56939-2024.md` и
матрицу `matrix.md`.

## Отслеживание

Статусы переводятся по гейтам конвейера; каждый перевод — записью
в `## Журнал статусов` реестра (append-only, конституция §5):

- `open` — предъявлено, не промоутнуто: `plan=none`.
- `planned` — план закрытия прошёл Owner-гейт старта кодинга
  (`Ready for Coder` → `In progress`): row обновляется
  (`plan=<PlanID>`, `статус=planned`), запись журнала
  `<ID>: open → planned — <PlanID>`.
- `verified` — план смержён (Owner-гейт `In review` → `Merged`,
  коммит `type(PlanID)`): Manager в Evidence-узле merge переводит
  статус, запись журнала `<ID>: planned → verified — <commit>`.

Изменение самого требования (формулировки, приоритета, срока) —
записью журнала `<ID>: требование изменено (<что>: <было> → <стало>) —
<почему>` с обновлением row той же правкой. Текущий статус реализации
и его изменения читаются из row + журнала (все четыре ветки 5.3.3.3:
принятие, текущий статус, изменения статуса, изменения требований).

## Критерии пересмотра

Пересмотр набора требований (5.3.2.4) — событийный; периодический
пересмотр НЕ проводится: в конвейере один Owner, каждое изменение
проходит через гейты, и событийные триггеры покрывают весь цикл
изменений. Триггеры:

- план в статусе `Superseded` — требования его R-меток пересматриваются
  первым же планом-преемником: возврат в `open` (запись
  `<ID>: planned → open — <PlanID superseded>`) либо перенос на
  преемника;
- изменение конституции (`AGENTS.md`), затрагивающее трассу требований
  (реестр, R-метки, каталоги) — пересмотр планом, внёсшим изменение;
- прямое решение Owner (бриф в чате) — ближайшим планом.

Каждый пересмотр — записью журнала (перевод статуса или «требование
изменено»); молчавший пересмотр не существует (§5: чего нет в файлах —
не существует).
